# 巡检知识内化管线(设计文档 v0.5)

> ⚠️ 未上线 · 暂缓：本稿引用的 `归档记忆/`、`.agents/skills/` 等尚不存在，暂缓推进，已从首页索引移出。要重启时再续。
> 起草:毛毛 | 审查:小花(内容)、ming(逻辑)| 批准:宇航员
> 状态:v0.5,试运行后修订
> 日期:2026-06-02(v0.5 修订:2026-06-03)

## 问题

巡检每天产出日志,大部分是"无需行动",偶尔有新发现。这些新发现看完就丢,下次遇到同类情况还得从头来。

## 目标

把巡检里发现的有用知识,自动沉淀成下次能直接调用的经验和技能。

宇航员不需要改任何日常流程。巡检照做、群聊照聊、文档照写。管线跑在后端,宇航员每周花五分钟看一眼本周编译成果,觉得有用就留,没用就删。

## 管线流程

```
巡检日志
  │
  ▼
┌─────────┐
│   Log   │  记录原始数据(谁/何时/何地/什么)
└────┬────┘
     │
     ▼
┌──────────┐
│ Quantize │  打标签:知识型/行动型/告警型/例行型
│          │  + 置信度:高/中/低
│          │  + topic:从词表选取
└────┬─────┘
     │
     ├─ 例行型 → 丢弃(只留计数 → 周基线偏差检测 → 偏差触发告警型管线)
     ├─ 告警型 → 直接通知 + 记入记忆
     │           └─ 反复出现≥3次/7天 → 升级为行动型
     ├─ 知识型 → 记忆库(pin_memory / searchable)
     │
     └─ 行动型 ──┬─ 轻型编译 → record_experience(即时)
                 │   └─ 低置信度:同类≥2条才触发
                 │
                 └─ 重型编译 → 新建/修改 SKILL.md(攒够后)
                     └─ 按 topic 分组,同 topic ≥3 条触发
```

## 各环节定义

### 1. Log(记录)

**输入:** 巡检原始产出(群聊消息、文件变更、外部信息等)

**输出:** 原始日志条目,保留完整上下文(时间戳、来源、原文)

**规则:**
- 原始日志始终保留,不压缩、不截断
- 后续环节引用日志时保留原文链接,不只存摘要

**日志采集方式(v0.3 新增,回应 hanako #3):**
日志怎么进 Quantize,取决于巡检类型:

| 巡检类型 | 采集方式 | 触发时机 |
|----------|----------|----------|
| 群聊巡检 | agent 群聊中触发式执行 | 每次群聊会话结束时自动提取 |
| 文件巡检 | 定时脚本(每日/每周) | cron 任务触发 |
| 外部信息巡检 | agent 主动抓取 | 配置的外部源有更新时 |

所有日志统一存入 `24帧运营库/00_系统/巡检日志/` 目录,按日期组织(YYYY-MM-DD.md)。Quantize 阶段从该目录读取。

### 2. Quantize(分类)

**输入:** 原始日志条目

**输出:** 带标签的日志条目(标签 + 置信度 + topic + 原文摘要 + 时间戳 + 来源)

**标签定义:**

| 标签 | 定义 | 示例 |
|------|------|------|
| 知识型 | 发现了新事实、新信息 | "上影节6月13日截止"、"某公众号改了更新频率" |
| 行动型 | 发现了可复用的做法、规则、改进方向 | "没回复消息→应加自验证规则"、"预算表要用固定模板" |
| 告警型 | 需要立即关注的问题 | "token即将过期"、"某接口返回错误" |
| 例行型 | 正常状态,无需行动 | "公众号今日无更新"、"所有接口正常" |

**置信度分层(v0.3 新增,回应 hanako #2):**

| 置信度 | 定义 | 编译行为 |
|--------|------|----------|
| 高 | 有明确证据,多次验证 | 单条即可触发轻型编译 |
| 中 | 有迹象但未充分验证 | 单条即可触发轻型编译 |
| 低 | 疑似/推测/单次观察 | 同类 ≥ 2 条才触发轻型编译 |

置信度由 Quantize 阶段判定。判定依据:
- 高:有多个独立来源佐证,或同一现象在不同时间重复出现
- 中:有直接证据但样本量不足(如只看到一次)
- 低:间接迹象、推测、单次异常

**来源追溯(v0.3 新增,v0.5 扩展:回应 ming #1 + hanako 试运行反馈):**
所有编译产物(不论置信度高低)必须标记 `sourceIds`(原始观察ID列表)和 `inferenceBasis`(推断依据)。

如果后续某条观察被证伪,可以:
1. 扫描所有引用该观察ID的编译产物
2. 标红挂起,等人工确认
3. 决定是删除、修改还是保留编译产物

不自动回滚,但自动暴露。

`inferenceBasis` 字段说明:
- 记录"这条 experience 是从什么观察推断出来的"
- 格式:简短描述(1-2句),说明推断逻辑
- 示例:"用户认可灵感库升格判断(观察)→ 推断需要定期回顾灵感库状态(行动)"
- 该字段与 `sourceIds` 配合使用:sourceIds 指向原始条目,inferenceBasis 解释推断逻辑

**topic 标签(v0.3 新增,回应 hanako #4 + ming #2):**
Quantize 阶段为每条行动型日志指定一个 topic,从预定义词表中选取(不自由输入)。

词表位置:`24帧运营库/00_系统/topic-词表.md`

初期词表(8 个):
1. `内容策略` - 公众号/内容方向、选题、风格相关
2. `发布节奏` - 更新频率、发布时间、排期相关
3. `社群运营` - 用户互动、社群维护、回复策略
4. `品牌建设` - 品牌调性、视觉、传播策略
5. `项目管理` - 预算、进度、协作流程
6. `技术运维` - 接口、token、系统配置、工具链
7. `外部信息` - 行业动态、竞品、政策变化
8. `其他` - 暂时无法归类的(后续扩充词表)

不在词表中的 topic 标为 `待归类`,由宇航员审查时决定是归入现有类目还是新增。

词表可随管线运行动态扩充,但初期保持收敛(≤ 20 个),避免分类过细导致每类都到不了阈值。

**例行型计数消费规则(回应 ming v0.1 #1):**
例行型日志本身丢弃,但保留每日计数。计数用途:
- 建立周基线(过去 4 周同日例行型数量的均值)
- 当某天例行型数量显著低于基线(降幅 > 50%)→ 触发告警,走告警型管线(v0.3 明确:归入告警型管线统一处理,不另开通道)
- 计数仅用于偏差检测,不进入编译管线

**灰色地带规则(回应 ming v0.1 #2):**
同一日志同时命中知识型和行动型时,走行动型管线,知识型材料作为附带写入记忆。
例如「某公众号改了更新频率」既是新事实(知识型),也可能触发「更新计划表」的行动规则(行动型)。此时:
- 行动型管线照常走轻型/重型编译
- 知识型材料(频率变化的具体数据)作为该 experience 条目的附带字段存入记忆
- 这样既能复用做法,也不会丢掉原始事实

**信息保留规则(回应 ming v0.1 问题):**
- 标签是分类标记,不替代原文
- 每个标签条目附带:原文摘要(1-2句)、时间戳、来源
- 轻型编译时使用压缩摘要 + 原文链接
- 重型编译时可回溯原文获取完整上下文

### 3. 告警升级规则(回应 ming v0.1 #4)

同一告警在 7 天内出现 ≥ 3 次 → 自动升级为行动型,走轻型编译。

升级时保留原始告警上下文(每次告警的时间戳和内容),编译产出的 experience 格式为:「反复出现X告警 → 检查根因 / 建立预防措施」。

升级后原始告警标签不变(仍为告警型),但新增一个 `upgraded_to_action: true` 标记,防止重复触发升级。

**例行型基线偏差告警(v0.3 新增,回应 hanako #1):**
例行型日志计数触发的基线偏差告警,走告警型管线,和其它告警一样处理。包括:
- 记入记忆
- 满足条件时升级为行动型
- 不单独开辟通道,统一归口

### 4. Compile - 轻型(即时编译)

**输入:** 行动型日志条目

**输出:** experience 记录(record_experience),附带 `sourceIds` 字段

**触发条件:**
- 高/中置信度:单条行动型日志即可触发
- 低置信度:同类(同 topic)≥ 2 条才触发

**操作:**
- 调用 record_experience,写入分类和内容
- 内容格式:「场景 + 做法」,如"巡检发现公众号未更新→检查是否有预告"
- 记录 `sourceIds`:本次编译所依据的原始观察ID列表(便于追溯回退)
- 记录 `inferenceBasis`:推断依据,说明这条 experience 是从什么观察推断出来的(v0.5 新增)
- 即时写入,成本低,错了容易回滚(unpin 或手动删除)

### 5. Compile - 重型(聚合编译)

**输入:** 同一 topic 的多条 experience 记录

**输出:** 新建或修改 SKILL.md 文件

**触发条件(同时满足):**
- 同一 topic 下累计 ≥ 3 条 experience(阈值可调)
- 距上次重型编译该 topic ≥ 7 天(防止频繁改动 skill 文件)
- 需要宇航员确认后才执行

**操作:**
- 按 topic 分组聚合相关 experience,提炼为带触发条件的完整策略
- 写入 `.agents/skills/<name>/SKILL.md` 或修改已有 skill
- 记录编译决策理由(哪几条 experience 聚合、为什么这样提炼)
- 记录 `sourceIds`:本次重型编译所依据的所有原始观察ID

### 6. Skill / Experience 分离

| 类型 | 存放位置 | 生命周期 | 示例 |
|------|----------|----------|------|
| 通用策略技能 | `.agents/skills/` | 长期,随项目演进 | 公众号分析框架、预算编制方法 |
| 临时知识 | 记忆库 | 有有效期,过期清理 | 上影节截止日、某人联系方式 |
| 原子经验规则 | experience 库 | 长期,可被重型编译聚合 | "遇到X做Y" |

### 7. 临时知识过期清理(v0.3 新增,回应 hanako #4)

**自动清理规则:**
- 知识型条目附带临时事实时,自动标记 `expireDays: 30`
- 30 天内无任何引用(未被查询、未被编译引用)→ 自动归档(移到 `24帧运营库/00_系统/归档记忆/`)
- 归档后仍可手动恢复,不删除

**兜底机制:**
- 写进宇航员每周五分钟工作项:「本周有 X 条临时知识即将过期,请确认是否保留」
- 宇航员可手动延长有效期或提前归档

## 验证门控

### 自动门控(脚本可执行)

编译产出 candidate 后,自动检查:

1. **冲突检测**:和现有 experience/skill 做关键词匹配,发现潜在冲突则标红
2. **重复检测**:和已有记录比对,避免重复写入
3. **格式检查**:experience 是否符合「场景+做法」格式,skill 是否有触发条件
4. **来源标记检查**:编译产物是否包含 `sourceIds` 字段(缺失则挂起)

自动门控不通过 → 挂起,等人工审查。

### 人工门控

| 操作类型 | 门控级别 |
|----------|----------|
| 新增一条 experience | 自动通过(轻型编译) |
| 修改已有 experience | 自动通过,记录变更 |
| 新建 SKILL.md | 宇航员确认 |
| 修改已有 SKILL.md | 宇航员确认 |

## 冲突解决

### 优先级链

1. 宇航员显式指令(最高)
2. 安全规则
3. 较新的规则覆盖较旧的
4. 未解决的冲突 → 升级给宇航员裁决

### 冲突清单格式

每次编译产出 candidate 后,如检测到潜在冲突,生成如下清单:

```
━━ 冲突清单 2026-06-02 ━━
候选规则:群聊消息应在5分钟内响应
潜在冲突:已有规则"讨论中不打断对话"(来源:协作机制规则.md 2026-06-02)
冲突描述:对方发了新消息但团队正在讨论中,快速响应会打断当前讨论
处理建议:加上下文判断--如果对方在等回复,优先响应;如果讨论中,等讨论段落结束后再响应
状态:待宇航员裁决
━━━━━━━━━━━━━━━━━━━━━
```

## 终止条件(防止编译循环)

### 轻型编译终止

- 单次写入即完成,无循环风险
- 如果 record_experience 后立即触发了新的巡检发现该规则有误 → 修改或删除该条 experience,不触发重新编译

### 重型编译终止

- **冷却期**:同一 topic 完成重型编译后,7 天内不触发该 topic 的下一次重型编译
- **最大迭代**:单次重型编译最多修改 1 个 skill 文件。如果编译过程中发现需要修改多个 skill → 拆成多次,每次独立审查
- **升级机制**:编译过程中检测到冲突且无法自动解决 → 挂起,等宇航员裁决,不继续编译

### 死循环检测

如果同一条 experience 在 30 天内被编译→修改→再编译超过 3 次 → 标记为"不稳定规则",暂停该条目的自动编译,等宇航员介入。

**不稳定规则存储(回应 ming v0.1 #3):**
在 experience 库的对应条目中增加 `is_stable: false` 字段(默认 `is_stable: true`)。标记为不稳定后:
- 该条目不再参与重型编译聚合
- 轻型编译仍可修改该条目内容,但每次修改时自动附加警告日志
- 宇航员审查后手动将 `is_stable` 恢复为 `true`,该条目重新参与编译
