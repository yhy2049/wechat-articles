## 核心判断

你已经有了宇航员的 80%。缺的不是再造机制，是收敛身份 + 接上触发。

余一最核心的一句话不是"复利工程"也不是"红黄绿灯"——是 **"环境 > 机制 > 反馈"** 和 **"AI is me"**。机制是商品化的，人人都有；环境（你的素材、审美、偏好）和反馈（你的验收标准、市场数据）才是让"AI 余鸿"区别于"AI 余一"的护城河。

所以宇航员不是一个大 prompt，是一个五层系统。你要做的是：把已有的机制层收拢成一个可挂载的身份，再把触发层自动化。

## 五层架构（DSH 映射）

### 1. 身份层 — 谁在执行

余一说的"AI is me"，落点是：这个 agent 知道你的口味、你的业务、你的验收标准。不是"它能做什么"，是"它像不像你"。

DSH 实现路径：
- `~/.dsh/.agent-presets/` 下建一个 astronaut preset（目前这个目录不存在）
- 挂载：ai-astronaut-core + full-auto-mode + async-communication + decision-light-system + compound-interest-engine + intent-understanding + agent-work-principles + general-capability-folder + avoid-repeat-loop + ai-cli-provider-config
- 挂载：AGENTS.md 中的用户画像（余鸿的业务、偏好、写作要求）
- 默认策略：红黄绿灯内置，绿灯自动推进、黄灯事后报告、红灯先说明

### 2. 机制层 — 怎么执行

已建成。10+ 个 skill 覆盖完整闭环：

| 余一的概念 | DSH skill | 作用 |
|---|---|---|
| 红黄绿灯决策 | ai-astronaut-core + decision-light-system | 自主决策边界 |
| 复利工程 | compound-interest-engine + ai-astronaut-core | 压缩到通用层、指向行动 |
| 异步沟通 | async-communication | 不打断工作流的需求传递 |
| 意图理解 | intent-understanding | 识别"发邮件"背后的"拿到文件" |
| 自主决策 | agent-work-principles | 不反问、直接行动、事后审计 |
| 通用能力文件夹 | general-capability-folder | 审美/设计模式跨 skill 复用 |
| 避免重复循环 | avoid-repeat-loop | 不陷入微调死循环 |
| AI CLI 配置 | ai-cli-provider-config | Claude Code/Codex 第三方 API |
| 知识飞轮 | knowledge-flywheel | 踩坑后写 shared_learning |

### 3. 环境层 — 拿什么执行

已建成。24帧运营库（5+1 目录结构）+ 通用能力文件夹。关键：审美用 HTML 示例而非文字描述（余一的原话："文字对 AI 不是很好理解的东西，不如展示"）。

### 4. 触发层 — 什么时候执行

**这是最大缺口，也是最大的设计选择。**

DSH 可用的触发手段：

| 方案 | 能力 | 局限 | 适合场景 |
|---|---|---|---|
| Goal 自动续跑 | 同一 session 内最多 256 轮自动续跑 | 需要有人启动一个 session | "给我一个长任务，你跑完再叫我" |
| 后台任务 + 子代理 | 并行执行，不阻塞主线程 | session 绑定 | 多任务并行、研究、批量处理 |
| Workflow 工具 | 脚本编排大量子代理 | session 绑定，一次性 | 大规模并行（批量调研、迁移、审计） |
| Cordis 动态插件（定时器/事件） | 真正的 hook 劫持 + 定时触发 | 需要写插件，目前未验证 | "每天凌晨自动跑一次复利压缩" |
| webhook-subscriptions | 外部事件触发 agent run | 需要外部事件源 | GitHub PR、邮件到达、数据变更 |
| DSH 内置 cron | 跨 session 定时任务 | 需确认 DSH 是否有 | "每 3 天自动压缩一次教学文档" |

**余一的做法**：hook 劫持 + 定时任务 + 异步沟通文件三件套。在 DSH 里等价的是：Cordis 插件定时器 + goal 自动续跑 + 异步沟通 skill。

**关键决策**：触发层选哪条路？这决定了宇航员是"你召唤它"还是"它自己跑"。

### 5. 反馈层 — 怎么进化

余一复利工程的核心三条：
1. 压缩到通用层（不是记细节步骤，是提炼底层模式）
2. 必须指向行动（不带动作的总结都是无效的）
3. 记录轨迹而非模板（记录决策轨迹和动作序列）

DSH 实现路径：
- 争议日志：dispute-log.md（ai-astronaut-core 已提到）
- 市场验证：真实数据反馈 → 给 AI → 自主分析 → 更新评估体系（棉手套案例）
- 复利压缩：compound-interest-engine skill + 定时触发（gap）
- 当场验证：造了机制要当场跑一遍（余一原话）

## 三个真缺口

### 缺口 1：身份未收敛

宇航员身份目前分散在：ai-astronaut-core skill、AGENTS.md、Hermes memory（迁移进 AGENTS.md）、散落的偏好。没有一个可挂载的、可版本管理的"宇航员"身份。

要解决：把身份收敛成一个 DSH agent preset。

### 缺口 2：触发未自动化

DSH 有 goal 自动续跑（session 内）、后台任务、workflow，但没有跨 session 的 cron/hook。宇航员目前只能"你召唤它"，不能"它自己跑"。

要解决：确认 DSH 是否有内置 cron；没有的话，用 Cordis 插件定时器或 webhook-subscriptions。

### 缺口 3：反馈闭环未验证

compound-interest-engine 和 ai-astronaut-core 里的复利工程是设计好的，但从未在 DSH 里跑通验证过。余一强调"造了机制要当场跑一遍"。

要解决：用一个真实任务跑一遍完整闭环（任务→复利→压缩→更新 skill→再次任务→验证改进）。

## 需要拍板的决策点

1. **身份形态**：宇航员是独立 DSH preset（新身份），还是扩展当前默认 agent（在 AGENTS.md 里加宇航员模式）？
2. **触发路径**：走 goal 自动续跑（手动启动、session 内）还是 Cordis 插件定时（自动触发、跨 session）？
3. **首批任务**：宇航员优先做什么？（采访稿处理 / 公众号文章 / 小红书图文 / 市场调研 / 其他）
4. **验收标准**：60 分验收 + 你付 token 代价（余一模式），还是要求更高？

---

## 建议的第一步

如果只做一件事，做这个：**用一个真实任务跑通一次完整的 异步沟通→意图理解→自主执行→复利压缩→更新 skill→验证 闭环。**

不需要先建 preset、不需要先搭 cron。先把反馈闭环跑通，验证机制在 DSH 里真的能转起来。跑通了再往上搭身份和触发。

理由：余一说"造了机制要当场跑一遍"，也说"不要既想要又不想付出代价"。先用最小成本验证机制能转，再投资身份和触发。

### 主动进化：自审机制

余一原话："每隔三天到一周会压缩一下。" 不是扩充，是找问题、压缩、指向action。

**已搭建**：

| 组件 | 路径 | 作用 |
|------|------|------|
| 自审 skill | `~/.agents/skills/astronaut-self-audit/SKILL.md` | 四步流程：读取现状→诊断问题→压缩→执行更新 |
| 触发脚本 | `~/Documents/async-communication/trigger-audit.sh` | 创建 pending-audit.md，宇航员下次启动时优先执行 |
| launchd 配置 | `~/Documents/async-communication/com.astronaut.self-audit.plist` | 每3天自动触发（需手动安装到 ~/Library/LaunchAgents/） |
| preset 集成 | `~/.dsh/.agent-presets/astronaut/agent.cordis.yml` | 宇航员启动时检查 pending-audit.md，存在则先自审 |

**自审四步**：
1. 读取现状（preset + dispute-log + 近期任务）
2. 诊断问题（重复问题/未触发规则/未触发复利）
3. 压缩到通用层（一句话描述问题 + 指向action）
4. 执行更新（改preset/加skill/改skill/删规则）

**铁律**：不扩充只压缩。每次自审只改 1-3 处。改完必须用下一个任务验证。
