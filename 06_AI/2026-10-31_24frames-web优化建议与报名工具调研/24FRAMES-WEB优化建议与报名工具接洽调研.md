## 一、现状结论（实测）

**功能上「能跑」，但离「真实运营」有硬缺口。**

本地 Wrangler + Playwright 实测通过：

| 模块 | 结果 |
| --- | --- |
| 首页 / 放映列表 / 活动详情 / 关于 / 帮助 / 后台概览 / 场地页 | 全部渲染，无控制台错误 |
| 选座（216 座）→ 填写信息 → 提交 → 支付 → 电子票 → 票夹 | 全链路通，订单号/二维码/座位正常 |
| 退票（>24h 允许）| 正常 |
| 现场核销（示例订单号 → 核销成功）| 正常 |
| 后台新建放映 / 场地维护 / 订单列表 | 正常 |
| 档案 302 篇：年份筛选 / 搜索 / 文章阅读 / 图片加载 | 正常 |
| 在线电影匹配 `/api/film-search?q=花样年华` | 豆瓣返回 3 条，正常 |
| 移动端 390px / 桌面 1440px | 无横向溢出 |

**已确认的技术特征：**
- 无构建静态 SPA：原生 HTML/CSS/JS，hash 路由（`#/` 开头）。
- 数据层 `localStorage`：`frames24_tickets_v3`（活动/订单/影院/影厅/座位）、`frames24_profile_v1`（购票人）。
- 支付为**模拟支付**；无登录；订单、座位、后台修改都只存在**当前浏览器**。
- 在线电影匹配走 Cloudflare Pages Functions（豆瓣/Wikidata）。
- 资源总量：JS ≈ 2.7MB（archive-20xx.js 按需懒加载）、字体 ≈ 1.9MB、图片 ≈ 3.6MB。

| --- | --- | --- | --- | --- |
| **B1** | 🔴 高 | 全站数据层 | 订单/座位/后台全部存 `localStorage`，**跨设备不同步**。现场核销和后台看不到观众手机上的订单；换设备/清缓存即丢 | 接服务端：Cloudflare D1(数据库) + Pages Function(API)。购票/退票/核销/候补都走 API，浏览器只做展示 |

| **B5** | 🟡 低 | `data.js:146` | `shengri`（生日快乐）`saleEnd: 2026-11-02T19:00` **晚于活动开始**（11-01 19:00），数据不严谨。当前因 `eventPhase` 先判 `date` 所以没实际坏，但值会误导 | `saleEnd` 改为活动开始时间 `2026-11-01T19:00:00+08:00`，与 `fuqi` 一致 |
| **B6** | 🟡 低 | 候补/审核/转让 | 都是前端演示逻辑，无服务端并发控制；多人同时买同一座会重复占座 | 服务端原子锁座（座位状态在 DB 里用事务更新） |

## 三、优化建议（按优先级）

### P0 · 真实运营必备
1. **服务端数据 + 登录 + 真实支付**（即 B1/B2/B3）。这是从「演示」到「能用」的唯一路径。
2. **后台数据看板补强**：加「核销率 / 到场率 / 候补转化 / 单场收支（票价×张数−手续费）」；按活动导出营收。
3. **防重复报名**：同手机号/微信号对同一活动限 1 单（当前靠 `limitPerOrder` 限张数，未限人）。

### P1 · 体验与性能
4. **字体优化**：当前中文子集 1.5MB + Montserrat 7 字重 ≈ 1.9MB。建议 `font-display: swap` 已可再加；把 Montserrat 按需 `unicode-range` 拆开；中文子集按「页面用字」进一步裁剪（目前是 GB2312 常用字，偏大）。
5. **档案加载**：archive-20xx.js 已按需懒加载（好），但打开 `#/archive` 一次拉全部年份 ≈ 2.1MB。建议拆成「每页 24 篇」增量拉取（现有 `limit:24` 只是前端分页，数据仍全量）。
6. **图片懒加载**：活动海报、档案封面加 `loading="lazy"`（档案 302 张封面全部加载会拖慢）。
7. **支付页主 CTA 固定**：手机端把「确认支付」固定在底部安全区，避免用户找不到按钮。

### P2 · SEO 与分享
8. **hash 路由改 History 路由或做预渲染**：`#/archive/xxx`、`#/event/xxx` 目前搜索引擎和微信分享都无法出干净链接，也不可被索引。至少给活动详情和档案文章加 `og:image`、`canonical`、JSON-LD（`Event` / `Article`）。
9. **站点 `sitemap.xml` / `robots.txt`**：目前无；建议为 302 篇档案 + 活动页生成。
10. **分享卡片**：微信/朋友圈转发时出「标题 + 海报 + 简介」；当前 `og:image` 缺失，转发多为空白缩略图。

### P3 · 可访问性与细节
11. 表单输入加 `aria-label` / `label for`（已基本具备）；座席按钮 `aria-pressed` 状态。
12. 深色主题下对比度（`#12100e` 背景 + 灰字）在部分小字号段落可能不足，抽查 WCAG AA。

## 五、接洽方案（如何把两者「做接洽」）

> 三个方向，按「真实运营投入」从小到大，给出推荐路径。

### 方案 A（推荐 · 轻量落地）：**自建站做「品牌 + 档案 + 选座入口」，小萝卜做「报名 + 收款 + 通知」**

- **怎么分工**：
  - 24FRAMES-WEB 保留：首页 / 关于 / 302 篇档案 / 活动详情 / 座位图展示（可只读或预览）。
  - 小萝卜负责：真实报名、微信支付收款、候补/审核/转让、核销、群发/订阅通知、数据导出。
- **怎么接**：每个活动的「立即报名 / 选座购票」按钮，直接跳转到对应小萝卜活动的 H5 链接或小程序卡片（`wx-open-launch-weapp` 或普通 `<a href="https://...">`）。在活动说明里放小萝卜活动码；公众号菜单挂小程序。
- **成本**：几乎零开发，0 工具费 + 0.6%~1% 微信支付手续费。
- **优点**：立刻能用真实收款和消息触达；档案和品牌视觉仍是自己的；不用自研支付/短信。
- **缺点**：选座要跳去小萝卜（如果介意「跳转体验」，可只对非选座场次用，选座场次继续走自建站，但收款仍是缺口）；两套系统数据不互通（需手动对账或用导入导出）。

### 方案 B（彻底自建）：**补齐服务端 + 微信支付 + 消息触达**

- 加 Cloudflare D1 + Pages Function：订单/座位/候补/核销走 API；接微信支付 JSAPI；接微信「订阅消息」或企微通知；加后台登录。
- **优点**：视觉、选座、数据全统一，长期可控；档案和票务在同一站。
- **成本**：开发量大（服务端 + 支付回调 + 并发锁座 + 通知），需要小程序/公众号资质与商户号；后续维护在自身上。
- **适用**：若选座体验是核心卖点、且愿意投入自研。

### 方案 C（混合 · 最平衡）：**自建站全保留，只把「收款 + 通知」外包给小萝卜**

- 自建站负责全部选座/报名/候补/核销的前端逻辑（现状），**收款这步跳转小萝卜**，支付结果回跳自建站并写入订单；或小萝卜仅作「收款 + 消息通知」，名单用导出导入回流。
- **优点**：选座体验最好；真实收款和通知有了；开发量中等（做支付回调 + 名单同步）。
- **缺点**：两套系统要对账；接洽/同步代码要写。

### 建议路线（务实）
1. **近期（1 场试跑）**：用**方案 A** 先跑通一场真实收费路演——用小萝卜收款 + 通知，自建站做宣传页 + 档案，验证「到场核销、退票、通知」流程。投入最小，立刻能上线。
2. **中期**：按试跑数据决定——若选座是强需求，升级到**方案 C**（自建站选座 + 小萝卜收款/通知）；若对跳转不敏感，沿用 A。
3. **长期**：若票务量稳定且要品牌统一，再评估**方案 B** 自研服务端，或与同类（互动吧 / 活动行 / 麦客 / 金数据）横向对比后选型。

> 注：互动吧、活动行（付费活动 + 微信收款）、麦客/金数据（表单收集）是同类可选项，本次未逐一深挖；若用户需要，下一轮可专项对比「收款费率、是否支持选座、是否支持候补/核销、数据导出、能否嵌入自建站」。

## 六、给用户的一页结论

1. **站本身能跑**：选座→支付→电子票→退票→核销→后台，全链路实测通过；无控制台错误；移动端不溢出。
2. **要「正常使用」必须先补三件事**：服务端数据（B1）、后台登录（B2）、真实微信支付（B3）。否则它只是「本机演示」，换台手机就看不到订单，也没法真收款。
3. **具体小 bug 两处**：支付页双按钮（B4）、`shengri` 售票截止时间晚于开场（B5）。改法见第二节，均 1 行改动量级。
4. **小萝卜的核心优势**：免费 + 真实微信收款（0.6%~1% 手续费）+ 微信消息触达（群发/订阅）+ 报名后私域引流 + 邀请分销。这几块正是自建站最缺的。
5. **接洽首选方案 A**：自建站做品牌/档案/选座，小萝卜做报名/收款/通知，先用一场真实路演跑通，再决定是否升级。
