## 〇、这轮深挖的核心发现（先说）

**自建站直接做「微信支付 / 微信登录 / 微信通知」大概率被一个硬约束卡住：域名未备案。**

- 线上域名 `https://frames24.cc.cd/` 是 `.cc.cd` 域名，**不是中国大陆 ICP 备案域名**。
- 微信 JS-SDK（自定义分享卡）、微信授权登录（OAuth）、微信支付（H5 / JSAPI）都要求：**绑定备案域名 + 公众号/小程序 + 商户号**。
- 结论：**在现有域名上，自建「真实微信支付 + 微信登录 + 微信通知」基本走不通**；要么换/加一个备案域名，要么把「收款 + 通知 + 登录」交给已备案的小程序工具（小萝卜）。

> 这一条改变了三条身份建议的实现路径：不是「做不做」，而是「在哪做」。详见第四节推荐路径。

## 一、真实运营的前置约束（决定路径）

| 约束 | 说明 | 影响 |
| --- | --- | --- |
| **域名备案** | `frames24.cc.cd` 未备案（`.cc.cd` 无法在大陆备案） | 微信支付 / 微信登录 / 微信分享 JS-SDK 全部受阻 |
| **微信支付资质** | 需营业执照（个体户/企业）+ 结算账户；小微商户有限额 | 收款要「企业/个体户 + 商户号」 |
| **服务端** | 现为纯静态 + Pages Functions；无数据库 | 订单/座位/核销要入库，需 D1/KV + API |
| **小程序/公众号** | 微信内闭环能力依赖小程序或服务号 | 通知、登录、支付都要依附其一 |
| **替代路径** | 小萝卜等已备案小程序自带商户+通知+登录 | 可承担收款/通知/登录 |

**对策**（两条路）：
- **路线 1（推荐，轻）**：小萝卜做「收款 + 通知 + 登录」，自建站做「品牌 + 选座 + 档案 + 核销台账」。自建站已有「报名渠道 → 外部报名工具」可对接。
- **路线 2（重，彻底自建）**：加一个**备案域名**（如 `24frames.cn`）+ 营业执照商户号 + 服务号/小程序，再接微信支付/登录/通知。适合要把票务完全握在自己手里、且愿意投入资质与开发。

## 二、P0 工程实现方案（若走路线 2 自建全栈）

> 以下为「服务端数据 + 登录 + 真实支付 + 并发锁座」的具体实现蓝图。

### 2.1 数据层（Cloudflare D1，字段级）
| 表 | 关键字段 |
| --- | --- |
| `events` | id, title, film, category, date, doors, endTime, duration, price, limitPerOrder, venue, hallId, cinemaId, saleStart, saleEnd, seatSelect, waitlist, reviewMode, channel(本站/外部), externalUrl, status, published, createdAt |
| `cinemas` | id, name, address, city, sort |
| `halls` | id, cinemaId, name, rows, cols, layout(JSON), aisles |
| `seats` | eventId, hallId, label, row, col, type(available/sold/blocked/accessible), status(free/held/sold), holdUntil, orderId |
| `orders` | id, orderNo, eventId, seats(JSON), qty, amount, fee, status(pending/paid/checked/refunded/rejected/waitlisted), channel, buyerName, buyerPhone, wechat, note, customFields(JSON), createdAt, paidAt, checkedAt, refundedAt, source |
| `waitlist` | id, eventId, phone, name, status(queued/fulfilled/cancelled), queueNo, createdAt |
| `checkins` | id, orderId, eventId, checkerId, checkedAt |
| `admins` | id, name, phone, role(super/checker/editor), createdAt |
| `audit_log` | id, adminId, action, target, detail, createdAt |

### 2.2 API（Pages Functions，`/api/*`）
| 端点 | 方法 | 说明 |
| --- | --- | --- |
| `/api/events` | GET | 公开活动列表（含余票/候补数） |
| `/api/events/:id` | GET | 活动详情 + 座位图状态 |
| `/api/seat-lock` | POST | 锁定座位（事务，10 分钟，过期释放） |
| `/api/orders` | POST | 创建订单（校验限购/防重复/座位占用） |
| `/api/orders/:id` | GET | 查订单（凭订单号+手机尾号） |
| `/api/checkin` | POST | 核销（防重复，写 checkins + audit） |
| `/api/auth/login` | POST | 管理员登录（密码 + 2FA 可选） |
| `/api/auth/wechat` | POST | 微信授权（需备案） |
| `/api/pay/notify` | POST | 微信支付回调（验签、幂等、占座） |
| `/api/pay/refund` | POST | 原路退款（记录退款单号） |
| `/api/admin/*` | — | 后台 CRUD（鉴权 + 角色校验） |

### 2.3 微信支付流程（路线 2）
1. 前端 `POST /api/orders` → 服务端事务锁座 + 创建 `pending` 订单 → 返回 `prepay_id`。
2. 前端调 `wx.requestPayment`（JSAPI）或跳转 H5。
3. 微信回调 `/api/pay/notify`：**验签 → 幂等（已 paid 则直接返回成功）→ 座位状态 held→sold → 订单 paid → 发通知**。
4. 退款：`POST /api/pay/refund` 走原路，记退款单号；全额退款≈0 交易，无手续费。
5. 对账：每日拉微信账单，比对订单状态。

### 2.4 鉴权与角色
- 管理员：邮箱+密码（argon2 哈希，服务端）或微信扫码（需备案）；角色 `super / checker / editor`。
- 所有 `/api/admin/*` 服务端校验 token + 角色；前端 `admin` 路由先过 `GET /api/auth/me`。
- 关键写操作（改价/退款/重置）记 `audit_log`。

### 2.5 并发锁座
- 座位状态机：`free → held(10min) → sold`；`held` 过期由定时任务/懒释放回 `free`。
- 用 D1 事务 + `UPDATE seats SET status='held' WHERE status='free'` 判断受影响行数=1 才成功，杜绝双卖。

## 四、推荐路径（受备案约束修正）

| 路线 | 做法 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- | --- |
| **1（推荐）** | 小萝卜做收款+通知+登录；自建站做品牌+选座+档案+核销台账 | 无需备案/商户号，立即能真收款；选座与品牌仍是自己的 | 名单两套需对账（已有 CSV 导入）；不能完全品牌闭环 | ✅ 先用一场真实路演验证 |
| **2** | 自建全栈 + 备案域名 + 商户号 | 品牌/数据全统一，长期可控 | 需备案域名 + 营业执照商户号 + 服务号/小程序 + 较大开发 | 票务量稳定后评估 |
| **3** | 混合：自建选座 + 小萝卜收款/通知（已有「外部报名渠道」对接） | 选座体验最好，收款/通知有 | 两套系统对账 + 写同步代码 | 若选座是强需求 |

**给运营者的执行顺序（结合备案约束）：**
1. **本周可做**：独立「合作」页（B1）+ 合作方 logo/联合呈现（B4）+ 合作案例筛选（B5）——纯前端，成本低，对拉片方/影院帮助大。
2. **近期（1 场试跑）**：路线 1 —— 用小萝卜收一场真实路演的钱 + 发通知；自建站活动详情跳外部报名（已有渠道），后台导入名单核销。验证「收款→核销→对账」闭环。
3. **中期**：服务端入库（C1）+ 后台登录（C2）+ 核销扫码（C4）——这几项不依赖备案，先把「数据 + 安全 + 现场」做扎实。
4. **长期**：若要微信支付/登录/分享闭环，再评估换备案域名走路线 2；否则持续用路线 1/3。

> **一句话**：备案约束让「自建微信支付/登录/通知」成本骤升；**近期最优解是小萝卜收款+通知（路线 1），自建站先把「合作页、数据入库、后台登录、扫码核销」做扎实**，等票务量起来再决定是否上备案域名自建全栈。
